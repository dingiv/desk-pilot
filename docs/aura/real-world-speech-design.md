# 真实场景语音听写：问题与设计

> 目标：让 aura 三层管道在真实对话中达到"听写级"体验——用户自然说话（含停顿、
> 口误、同音歧义），系统输出完整、正确、带标点的文字。
> 北极星：[[ai-secretary-north-star]]。

## 问题全景

将真实说话中的语音现象分为 **6 类**，每类有不同的根因和处理层：

### 1. 停顿碎片化 ⠂⠂⠂ 🔴 P0

**现象**：用户说"帮我把…（停顿 1.5s）…会议文件…（停顿 1.2s）…改成 markdown"，
VAD 在每个停顿切 EOS，产生 3 个碎片段。

**根因**：VAD 切段灵敏度与"什么算一句话"混为一谈。为了响应快（停顿一过立即出 batch
结果），`min_silence` 必须保持小（1.0s）——代价是长句在思考间隙被强切成碎片。

**处理层**：Stage1（VAD + 段合并）

**方案（2026-08-04 设计明确）**——`min_silence` 与 `merge_gap` 解耦，共同构成
**"中等间隔多句 merge"窗口**：
- **流式保响应**：scout 音频碎片不断追加进流式模型（Zipformer），每 15 帧出 streaming
  partial（`Interim`）。
- **低阈值触发 batch**：VAD 静音 ≥ `min_silence`（1.0s）即 EOS → 立即对累积 PCM 跑一次
  batch 识别（`Stage1Action::Batch`，普通 Batch 动作）→ Stage2 增量校准 →
  `CalibratedInterim` 同一 seq **就地更新**已有句子（不产生新句）。阈值低 → 停顿一过
  文字立刻出现。
- **补救 = 中等间隔合并**：`SegmentMerger` 按**时间戳**（`sos - last_seg_end_at`，精确测量
  真实句间静音——SOS/EOS 同时发出的自消除性质）判断相邻碎片间隔。间隔 < `merge_gap`
  → 吸收进同一 utterance，PCM 拼接后重跑 batch，结果更新已有句子；间隔 ≥ `merge_gap`
  → 上一句定稿（`Stage1Action::MergeBatch`，大 MergeBatch 动作）。窗口下界由
  `min_silence` 天然保证（不到 1s 的停顿根本不会切段），上界即 `merge_gap`。合并后重跑
  batch = 对整段做权威转写，校准结果替换句子的旧内容。0 = 关闭合并。
- **两种动作 = Stage2 的监听输入**（`Stage1Action`，与 `Utterance` 载荷一起定义在
  aura-asr 的数据契约区）：Batch（provisional，不写 ContextWindow）与 MergeBatch
  （authoritative，写 ContextWindow）都会触发 Stage2 纠偏——composer 的 Stage2 worker
  只消费这一个枚举。

**验证**：说"帮我把会议文件…（停 3s）…改成 markdown" → 1 段 final 而非 2 段；
停顿 6s → 2 段。

#### 1a. 段边界损失（拼接后"开头/结尾掉字"）🔴 已修复 2026-08-04

**现象**：拼接开启后，一个合并 utterance 的**开头或结尾偶尔掉 1-2 个字**（每段边界都
贡献一对损失，拼接把分散的损失集中到句内）。

**根因**（sherpa-onnx 1.13.4 `voice-activity-detector.cc` + `silero-vad-model.cc`）：
Silero VAD 的段边界 = **概率跨 threshold 的窗口**，不是真实语音边界——
- **段头**：`start_` 只回溯到 `temp_start_`（prob 首次 > threshold 的窗口）。轻声/弱辅音
  起音概率低于 threshold → 检测延迟 → 首字丢失。
- **段尾**：段截止于 `temp_end_`（prob 首次跌破 threshold 的窗口）。句尾弱化、韵尾渐弱
  → 尾字丢失。（`min_silence` 观察期内的音频只是被"算作静音"，不在段内。）

**方案**：`VadConfig.edge_margin_s`（默认 0.3s，0 = 关闭）——`OnnxVad` 维护全量样本的
recall 缓冲（60s），EOS 时用 `SpeechSegment::start()`（绝对样本偏移）把段头/段尾各扩展
`edge_margin_s` 的真实音频（头：onset 前的软起音；尾：fade 后的弱尾音——EOS 判定晚
`min_silence`，这段音频必然已流过）。上一段的**扩展后** end 作为下一段头扩展的下限，
拼接处永不重叠（不会产生重复文本）。纯函数 `segment_extension` 有单测。

### 2. 语气词污染 ⠂⠂ 🟡 P1

**现象**："嗯那个就是我想说的是呢这个这个功能它其实是比较简单的对吧"。
ASR 忠实转写，但 Stage2 要去掉所有无意义语气词。

**根因**：ASR 该不该去？答案是不——ASR 保持忠实转写（它不知道哪些是语气词哪些是实词）。
去语气词是 Stage2 的职责，因为它需要语义理解。

**处理层**：Stage2

**方案**：
- **few-shot 示例**：默认示例当前**已注释**（prompt.rs `DEFAULT_FEW_SHOT`）——需开启时
  取消注释或由调用方 `.few_shot()` 注入：
  ```
  原文：嗯那个蛇声长度需要增加一节
  纠偏：蛇身长度需要增加一节。
  ```
- **OUTPUT 指令**："去口语"规则当前**已注释**（prompt.rs OUTPUT 段后）——现役规则只有
  加标点/修错字/英文规范/专有名词四条
- **保守策略**：不确定是不是语气词时保留（避免误删实词）
- **Qwen2.5-3B 实测**（规则启用期间）：口语化用例已通过 ✅

**现状**（2026-08-17）：机制在（few-shot + 指令位都保留），但**默认关闭**——启用前
需重验 Qwen2.5-3B 在无"去口语"指令下的口语清洁度（Qwen3-ASR 批式转写本身较干净，
可能不再需要该规则）。

### 3. 同音歧义 ⠂⠂⠂ 🟡 P1

**现象**：ASR 输出 "计分起"——是"计分器"还是"计分起"（动作）？同音不同义。

**根因**：ASR 无法区分（音相同），需要上下文 + 语义理解。

**处理层**：Stage2（纠偏）+ Stage3（热词/纠偏反馈）

**方案**：
- **热词系统**（部分在役）：热词烘进 **Stage1 流式 recognizer**（boot 时 beam bias，
  StreamingAsrConfig.hotwords）+ 预载 Stage2 共享 store；**Stage2 prompt 的热词块当前已
  注释**（prompt.rs）——小模型对长热词列表遵循不佳，纠偏主要靠批式 Qwen3-ASR 质量 +
  用户纠正。Stage3 自动提取大写专名写入共享 store（运行时只进 LLM 层，下沉 ASR 是 M5）。
- **用户纠偏**（已有）：POST /api/correct → CorrectionStore → Stage2 权威示例
- **few-shot 示例**："计分起→计分器"、"蛇声→蛇身"（默认注释，可 `.few_shot()` 注入）
- **置信度保守**：prompt 已写"只修改确信是错误的部分，不确定就保留原文"
- **问题**：Qwen2.5-3B 对中文同音字的判断能力有限——部分能修（蛇声→蛇身 ✅），
  部分不能（计分起→计分器 时有时无）。这是模型能力上限。

**后续**：7B+ 模型会显著改善；用户纠偏是最可靠的手段（已实现）。

### 4. 口误自纠 ⠂⠂ 🟢 P2

**现象**：用户说"帮我用 rost… 不对… Rust 写个游戏"。
ASR 转出两段："帮我用 rost 写个游戏" + "不对 Rust 写个游戏"。

**根因**：人类说话时会自我纠正，但 ASR 不知道"不对"后面的内容是纠正。

**处理层**：Stage1（检测）→ Stage2（应用）

**方案**：
- **模式匹配**（正则）：检测 `…不对…` / `…不是…` / `…应该是…` 模式
- **去掉纠正前内容**：`rost…不对…Rust` → 直接用 `Rust`
- **实现**：在 calibrator.rs 的 calibrate() 里，发送给 LLM 之前先预处理：
  ```rust
  fn detect_self_correction(text: &str) -> String {
      // "rost 不对 rust" → "rust"
      // "计分起 不是 计分器" → "计分器"
      // 正则: (.+?)\s*(?:不对|不是|应该是)\s*(.+)
  }
  ```
- **优势**：零 LLM 开销，确定性逻辑。

### 5. 中英混排格式 ⠂ 🟡 P1

**现象**："打开Docker然后运行docker compose up" → 期望 "打开 Docker，然后运行 docker compose up。"

**根因**：ASR 不加空格（中英直接拼接），不加大写。

**处理层**：Stage2

**方案**：
- **OUTPUT 指令**（已有）："英文单词前后加空格"
- **few-shot 示例**：需要增加中英混排示例
- **Qwen2.5-3B 实测**：中英混排用例部分通过（加了逗号和 Docker 空格，但格式不完美）
- **代码后处理**（备选）：如果 LLM 没加空格，正则补：`([一-龥])([a-zA-Z])` → `$1 $2`

---

### 6. 断句与标点 ⠂⠂ 🟡 P1

**现象**：ASR 无标点输出长句 → 需要根据语义加逗号、句号。

**根因**：ASR 不负责标点（它只转写声音）。标点是 Stage2 的核心职责。

**处理层**：Stage2

**方案**：
- **OUTPUT 指令**（已有）："加标点（逗号、句号、问号等）"
- **Qwen2.5-3B 实测**：精简 prompt 后部分通过（短句✅，长句部分加标点）
- **问题**：复杂长句的断句位置不稳定（"这个问题，我们先将…" vs "这个问题。我们先将…"）

**后续**：这是模型理解能力的问题——3B 模型对长句语义分析能力有限。7B+ 会改善。

---

### 7. 连读与吞音 ⠂ 🟢 P2

**现象**：英文连读 "the tribal chieftain" → ASR 可能输出 "the tribal chief then"。
中文吞音 "整理成" → 可能变成 "整理层"。

**根因**：ASR 模型的声学模型能力限制——连读/吞音时声学特征模糊。

**处理层**：Stage1（选更好的 ASR）+ Stage2（纠偏）

**方案**：
- **ASR 层**：Qwen3-ASR 比 SenseVoice 在英文连读上好很多（实测：chief→chieftain 差异消失）
- **Stage2**：部分能修（蛇声→蛇身 ✅），但英文连修能力有限
- **用户纠偏**：最可靠的兜底（已实现）

---

### 8. 背景噪声干扰 ⠂ 🟢 P2

**现象**：环境噪声 → VAD 误判为语音 → ASR 产生垃圾文本。

**根因**：VAD threshold 太敏感（0.5），或麦克风无降噪。

**处理层**：Stage1（VAD）+ 前端（降噪）

**方案**：
- **VAD 调参**：threshold 0.5→0.6 减少误触发（代价：轻声说话可能丢）
- **噪声阈值检测**：在 executor 里加 RMS 能量门限，低于阈值的帧不送 VAD
- **前端降噪**：scout 层加 RNNoise/WebRTC VAD 预处理（远期）
- **垃圾过滤**：Stage2 对极短文本（<2 字且无语义）直接丢弃

## 已解决：停顿碎片化 ✅

- **段合并**（SegmentMerger，2026-08-04 设计明确）：`min_silence`（1.0s，低阈值保响应）
  与 `merge_gap`（内置默认 5.0s，aura.yaml 可配，中等间隔窗口上界）解耦；时间戳判断句间
  静音，间隔 < merge_gap
  吸收拼接 + 重跑 batch + 同一 seq 就地更新；≥ 则定稿。
- **段边界损失**（edge_margin_s 0.3s，见 §1a）：VAD 段边界 = threshold 交叉而非语音边界，
  扩展修复软起音/弱尾音丢失。
- 停顿碎片化从"说 1 句话出 3 段碎片"变成"出 1 段完整句"。
- 未来可调：merge_gap 调小（命令式场景，更快定稿）/ 调大（长句场景，更少切碎）。
